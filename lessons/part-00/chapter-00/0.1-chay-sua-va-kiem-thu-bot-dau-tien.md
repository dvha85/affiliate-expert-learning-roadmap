# Bài 0.1 — Chạy, sửa và kiểm thử Bot đầu tiên

> Mục tiêu là hoàn thành một vòng edit → run → test. Bạn chưa cần học Go tổng quát.

## 1. Trigger — Vì sao cần bài này ngay bây giờ?

M00 yêu cầu tạo quyết định đầu tiên, nhưng trước hết cần chứng minh workspace chạy được và test thật sự bảo vệ behavior.

## 2. Try First — Thử trước trong 10 phút

Từ learner workspace, chạy:

~~~bash
go run ./cmd/bot
go test ./...
~~~

Ghi nguyên output. Sau đó đổi một dòng text có ý nghĩa trong Bot, chạy lại và quan sát test.

## 3. Observe — Ghi điều thực sự xảy ra

Lưu bốn mục:

- command đã chạy;
- output trước thay đổi;
- output/test sau thay đổi;
- đây là evidence kind test, chưa phải market evidence.

Nếu command không chạy, phân biệt lỗi thiếu Go/path với lỗi code/test.

## 4. Minimum Knowledge — Kiến thức tối thiểu

- package main cho biết đây là executable package.
- func main là entry point.
- go run chạy chương trình; go test chạy các behavior checks.
- Test PASS chỉ chứng minh requirement đã mã hóa, không chứng minh Bot hiểu Affiliate.

Chưa cần interface, database, concurrency hay AI.

## 5. Apply — Áp dụng ngay

Chọn một thay đổi nhỏ, ví dụ thêm dòng nói rõ evidence mode hiện tại. Cập nhật test để behavior mới được bảo vệ.

~~~text
Before: Bot chỉ in trạng thái.
Change: Bot in thêm điều learner muốn kiểm soát.
After: output mới xuất hiện và test PASS.
~~~

## 6. Test a Failure — Kiểm thử tình huống lỗi

Tạm đổi expected output trong test để test FAIL. Đọc message, khôi phục expectation đúng và chạy tới PASS.

Điều không được xảy ra: xóa test chỉ để có màu xanh.

## 7. Evidence — Bằng chứng áp dụng

Lưu output trước/sau, một failure message, PASS cuối và code diff/commit vào artifact M00.

## 8. Checkpoint — Tự kiểm tra nhanh

1. go run và go test trả lời hai câu hỏi khác nhau thế nào?
2. Test xanh đã chứng minh điều gì và chưa chứng minh điều gì?
3. Vì sao cần tạo failure có chủ ý?

<details>
<summary><strong>Đáp án/rubric</strong></summary>

- run chứng minh executable behavior; test so behavior với expectation;
- test chỉ bảo vệ requirement hiện có, không xác nhận business truth;
- failure có chủ ý chứng minh test có khả năng phát hiện sai lệch;
- blocking misconception: coi test PASS là bằng chứng thị trường.

</details>

## 9. Explain-back — Giải thích lại

Giải thích vì sao một thay đổi nhỏ có test tốt hơn một thay đổi lớn không có output/evidence rõ.

## 10. Applied / Retry — Kết quả

- [ ] đã quan sát FAIL rồi khôi phục PASS;
- [ ] evidence đã lưu;
- [ ] explain-back phân biệt được software evidence và business evidence.
