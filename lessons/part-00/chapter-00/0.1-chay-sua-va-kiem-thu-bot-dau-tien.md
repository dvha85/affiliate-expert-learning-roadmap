# Bài 0.1 — Chạy, sửa và kiểm thử Bot đầu tiên

> **Mục tiêu của bài này không phải là học Go.**  
> Mục tiêu là giúp bạn — kể cả khi chưa từng lập trình — hiểu được vòng làm việc cơ bản nhất khi xây Bot:
>
> ```text
> nhìn trạng thái hiện tại
> → chạy chương trình
> → thay đổi một hành vi nhỏ
> → viết/đổi test để kiểm tra hành vi đó
> → quan sát test FAIL
> → sửa code
> → chạy lại đến PASS
> → giải thích được bằng chứng vừa tạo ra
> ```

Bài này là nền móng của toàn bộ chương trình. Sau này Bot sẽ đọc dữ liệu Affiliate thật, xếp hạng sản phẩm, gọi AI, chạy watcher và tự động hóa có kiểm soát. Nhưng dù hệ thống phức tạp đến đâu, bạn vẫn luôn quay về một câu hỏi rất cơ bản:

> **“Tôi thay đổi điều gì, tôi kiểm tra nó bằng cách nào, và bằng chứng nào cho thấy nó hoạt động đúng?”**

---

## 1. Bạn đang xây cái gì?

Trong repo này, sản phẩm xuyên suốt là một **Affiliate Intelligence Bot**.

Hiểu đơn giản, Bot trưởng thành sau này sẽ hỗ trợ các câu hỏi như:

- sản phẩm nào đáng xem xét;
- vì sao;
- bằng chứng nào hỗ trợ;
- dữ liệu nào còn thiếu;
- khi nào nên hành động;
- khi nào nên chờ;
- khi nào phải yêu cầu con người duyệt.

Nhưng ở Bài 0.1, Bot **chưa thông minh theo nghĩa kinh doanh**. Nó chỉ là một chương trình nhỏ đã có sẵn để bạn học cách làm việc với một hệ thống thật.

Starter Bot hiện tại có thể:

1. đọc một file dữ liệu mẫu;
2. tính một baseline score đơn giản;
3. in ranking;
4. in trạng thái như `RANK_SCENARIO`;
5. chạy automated tests.

Điều quan trọng nhất:

> **Bot chạy được ≠ Bot hiểu Affiliate.**

Đây là tư duy bạn phải giữ từ ngày đầu tiên.

## 2. Trước khi chạy: hiểu workspace của bạn

Từ repo root, learner workspace nằm tại:

```text
lab/learner/affiliate-bot/
```

Một số thành phần bạn sẽ gặp:

```text
lab/learner/affiliate-bot/
├── cmd/
│   └── bot/
│       ├── main.go
│       └── main_test.go
├── data/
├── internal/
└── go.mod
```

Bạn chưa cần hiểu toàn bộ cấu trúc này. Chỉ cần biết:

| Thành phần | Hiểu đơn giản |
|---|---|
| `cmd/bot/main.go` | nơi chương trình Bot được khởi chạy |
| `cmd/bot/main_test.go` | các kiểm tra tự động cho behavior của Bot |
| `data/` | dữ liệu Bot dùng để chạy |
| `internal/` | logic bên trong Bot |
| `go.mod` | khai báo đây là một Go module |

### Từ khóa đầu tiên: behavior

Trong khóa học này, **behavior** nghĩa là hành vi quan sát được của hệ thống.

Ví dụ:

```text
Khi Bot chạy với dữ liệu mẫu,
Bot phải in:
Phiên bản Bot (Bot version): pre-v0.1
```

Đó là một behavior.

Hoặc:

```text
Khi dữ liệu chưa đủ,
Bot phải trả trạng thái GET_MORE_DATA.
```

Đó cũng là một behavior.

Ta không học code chỉ để “biết syntax”. Ta thay đổi code để tạo ra behavior mong muốn và dùng test để bảo vệ behavior đó.

## 3. Hai lệnh quan trọng nhất của bài

Từ learner workspace:

```bash
cd lab/learner/affiliate-bot

go run ./cmd/bot
go test ./...
```

Hai lệnh nhìn giống nhau nhưng trả lời **hai câu hỏi hoàn toàn khác nhau**.

### 3.1 `go run ./cmd/bot`

Câu hỏi nó trả lời là:

> **“Nếu tôi chạy Bot ngay bây giờ, chuyện gì xảy ra?”**

Bạn đang quan sát chương trình như một người sử dụng.

Output có thể giống:

```text
Affiliate Bot đang khởi động...
Phiên bản Bot (Bot version): pre-v0.1
Loại bằng chứng (Evidence kind): synthetic (...)
Số quan sát (Observations) đã nạp: 3
Phiên bản công thức (Formula version): commission-per-order/v1
...
Trạng thái quyết định (Decision state): RANK_SCENARIO (...)
```

Đây là **runtime evidence**: bằng chứng về điều chương trình đã thực sự làm khi chạy.

### 3.2 `go test ./...`

Câu hỏi nó trả lời là:

> **“Behavior hiện tại có còn đúng với những expectation mà chúng ta đã mã hóa trong test không?”**

Nếu test PASS:

```text
ok   ...
```

nghĩa là các expectation hiện có đã được thỏa mãn.

Nếu test FAIL, Go sẽ chỉ ra nơi expectation và behavior không khớp.

### 3.3 Một nhầm lẫn rất quan trọng

Sai:

```text
Test PASS → Bot đang đưa ra quyết định Affiliate đúng.
```

Đúng:

```text
Test PASS → code đang đáp ứng các behavior mà test hiện tại kiểm tra.
```

Test có thể kiểm rằng:

```text
Bot in "RANK_SCENARIO"
```

nhưng test đó **không chứng minh**:

```text
sản phẩm đứng #1 thực sự là sản phẩm Affiliate tốt nhất ngoài thị trường.
```

Bạn vừa chạm vào một nguyên tắc sẽ theo toàn bộ chương trình:

> **Software evidence và business evidence là hai loại bằng chứng khác nhau.**

## 4. Đọc `main.go` mà không cần biết Go

Bạn sẽ thấy đầu file:

```go
package main
```

Hiểu đơn giản:

> File này thuộc chương trình có thể chạy trực tiếp.

Cuối file bạn sẽ thấy:

```go
func main() {
    ...
}
```

Hiểu đơn giản:

> `main()` là điểm bắt đầu khi chương trình được chạy.

Bạn cũng sẽ thấy các dòng như:

```go
fmt.Fprintln(out, "Affiliate Bot đang khởi động...")
```

Chưa cần học `fmt`, `io.Writer` hay function signature. Chỉ cần quan sát:

> Dòng code này tạo ra một dòng text mà bạn nhìn thấy khi chạy Bot.

### Mô hình tinh thần đơn giản

Hãy hình dung:

```text
main.go
  ↓
chương trình chạy
  ↓
Bot tạo output
  ↓
bạn quan sát output
```

Trong bài sau, mô hình sẽ mở rộng thành:

```text
input evidence
  ↓
Bot logic
  ↓
decision output
```

Nhưng hiện tại chỉ cần làm chủ vòng nhỏ nhất.

## 5. Đọc `main_test.go` như một bản hợp đồng

Trong test hiện tại có đoạn tương tự:

```go
for _, want := range []string{
    "Affiliate Bot đang khởi động...",
    "Phiên bản Bot (Bot version): pre-v0.1",
    ...
} {
    if !strings.Contains(out.String(), want) {
        t.Fatalf(...)
    }
}
```

Bạn chưa cần hiểu cú pháp đầy đủ.

Ý nghĩa nghiệp vụ của đoạn này là:

```text
Chạy Bot.
Lấy output.
Kiểm tra output có chứa từng câu bắt buộc hay không.
Nếu thiếu → test FAIL.
```

Vì vậy, test là một dạng **executable contract** — hợp đồng có thể chạy được.

Thay vì chỉ viết tài liệu:

```text
Bot nên in formula version.
```

Ta có thể viết test:

```text
Nếu output không có formula version → FAIL.
```

Khi requirement trở thành test, hệ thống có khả năng tự phát hiện regression tốt hơn.

## 6. Vòng thực hành chính: RED → GREEN

Bây giờ bạn sẽ thực hiện vòng quan trọng nhất của bài.

### Bước 1 — Chạy baseline

```bash
go run ./cmd/bot
go test ./...
```

Ghi lại:

```text
RUN baseline:
TEST baseline:
```

Bạn cần biết trạng thái **trước khi thay đổi**.

Nếu không có baseline, sau này bạn không biết lỗi mới là do mình tạo ra hay đã tồn tại từ trước.

---

### Bước 2 — Chọn một behavior rất nhỏ

Ví dụ muốn Bot in thêm:

```text
Giả định yếu nhất (Weakest assumption): chưa có dữ liệu conversion thực tế
```

Tại sao chọn thay đổi nhỏ?

Vì khi mới học, một thay đổi nhỏ giúp bạn dễ trả lời:

```text
Tôi vừa thay đổi điều gì?
Test nào liên quan?
Failure nào do thay đổi này gây ra?
```

Đừng thêm database, AI, API hay một ranking formula mới ở Bài 0.1.

---

### Bước 3 — Sửa test trước

Thêm expectation mới vào test.

Ví dụ về ý tưởng:

```go
"Giả định yếu nhất (Weakest assumption):"
```

Chạy:

```bash
go test ./...
```

Lúc này test **nên FAIL** vì Bot chưa in dòng đó.

Đây không phải thất bại của bạn.

Đây là evidence rất có giá trị:

> **Test mới thực sự có khả năng phát hiện behavior đang thiếu.**

Nếu bạn thêm một assertion nhưng test vẫn PASS ngay lập tức, cần kiểm tra:

- behavior đó đã tồn tại rồi?
- assertion có thực sự kiểm đúng thứ bạn nghĩ không?
- test có chạy đúng code path không?

---

### Bước 4 — Đọc failure message

Đừng vội sửa ngay.

Hãy đọc failure như một nguồn evidence.

Tự điền:

```text
Expected:
Observed:
Difference:
```

Ví dụ:

```text
Expected:
output có "Giả định yếu nhất (Weakest assumption):"

Observed:
output không có dòng này

Difference:
behavior mới chưa được implement
```

Đây là bước đầu của debugging có kỷ luật.

---

### Bước 5 — Sửa code tối thiểu

Thêm behavior tương ứng vào `main.go`.

Sau đó chạy:

```bash
go test ./...
```

Nếu PASS, chạy tiếp:

```bash
go run ./cmd/bot
```

Bạn cần cả hai:

- test cho thấy expectation được thỏa;
- runtime output cho thấy behavior người dùng thật sự nhìn thấy.

## 7. Vì sao phải cố ý nhìn thấy test FAIL?

Người mới thường nghĩ:

> “Mục tiêu là test xanh, vậy FAIL là xấu.”

Không hoàn toàn đúng.

Một test chưa từng được chứng minh là có thể fail có thể là test yếu.

Ví dụ bạn viết:

```text
Test rằng Bot có formula version.
```

Nhưng nếu xóa formula version khỏi code mà test vẫn PASS, test đó không bảo vệ behavior như bạn tưởng.

Vì vậy chu trình:

```text
FAIL có chủ ý
→ implement/fix
→ PASS
```

cho bạn hai bằng chứng:

1. test biết phát hiện sai;
2. implementation hiện tại đáp ứng expectation.

Đây là lý do Bài 0.1 yêu cầu lưu một failure message.

## 8. Test PASS chứng minh gì — và không chứng minh gì?

Đây là phần quan trọng nhất của bài.

Giả sử output là:

```text
1. Product B | score=9.60
2. Product A | score=7.00
```

Và test PASS.

### Test PASS có thể chứng minh

- code chạy;
- cùng input tạo ra output theo formula hiện tại;
- ranking tuân theo expectation đã viết;
- required text xuất hiện;
- một số failure path được xử lý như test mô tả.

### Test PASS không chứng minh

- Product B là sản phẩm Affiliate tốt nhất;
- người dùng thực sự muốn mua Product B;
- Product B có conversion rate tốt;
- seller đáng tin;
- commission cuối cùng sẽ được validation;
- chiến dịch sẽ có lợi nhuận;
- formula hiện tại là formula tối ưu.

### Vì sao?

Vì hiện tại formula chỉ là một **mô hình đơn giản**.

Nếu baseline là:

```text
price × commission_rate
```

thì score chỉ cho biết:

> “Trong dữ liệu hiện có, theo công thức hiện tại, commission-per-order giả định của sản phẩm này cao hơn.”

Nó không biết:

- demand;
- audience fit;
- click-through rate;
- conversion rate;
- refund risk;
- competition;
- compliance risk;
- content potential.

Vì vậy trạng thái `RANK_SCENARIO` rất quan trọng.

Nó có nghĩa:

> **“Bot đang xếp hạng theo một scenario/baseline, chưa phải khuyến nghị kinh doanh đã được xác nhận.”**

## 9. Vì sao giữ nguyên `RANK_SCENARIO`?

Trong output, người học đọc tiếng Việt nhưng một số token vẫn được giữ nguyên:

```text
RANK_SCENARIO
GET_MORE_DATA
HUMAN_REVIEW
RECOMMEND
```

Lý do:

### Với con người

Ta thêm diễn giải:

```text
RANK_SCENARIO (xếp hạng kịch bản; chưa phải khuyến nghị hành động)
```

### Với máy và code

Token `RANK_SCENARIO` có thể được dùng bởi:

- test;
- JSON schema;
- downstream code;
- logs;
- decision contract;
- automation sau này.

Nếu đổi tùy hứng thành:

```text
XEP_HANG_KICH_BAN
```

có thể phá contract kỹ thuật.

Nguyên tắc của repo:

> **Machine token ổn định; learner-facing explanation ưu tiên tiếng Việt.**

Ví dụ:

```text
go run ./cmd/bot
```

Ví dụ:


Ví dụ sau này:

Đây là ranh giới cực kỳ quan trọng.

```text

≠
data đúng
≠
model đúng
≠
decision kinh doanh đúng
```

Một Affiliate Intelligence Bot đáng tin phải kiểm soát từng lớp này.

## 11. Khi gặp lỗi, đừng sửa ngẫu nhiên

Ví dụ `go run` không chạy.

Không nên nghĩ ngay:

```text
Code hỏng.
```

Có thể là:

```text
Go chưa cài
sai folder
không đứng trong module
file path sai
code compile lỗi
test lỗi
```

Dùng tư duy phân lớp:

```text
Environment
  ↓
Build/compile
  ↓
Runtime
  ↓
Test
  ↓
Business logic
```

Nếu terminal báo:

```text
zsh: command not found: go
```

thì đây là **environment problem**, chưa phải logic problem.

Nếu `go test` báo thiếu expected text, đó là **behavior/test mismatch**.

Học cách gọi đúng tên loại lỗi giúp bạn debug nhanh hơn rất nhiều.

## 14. Checkpoint kiến thức

Tự trả lời trước khi mở đáp án.

### Câu 1

`go run` và `go test` khác nhau thế nào?

### Câu 2

Vì sao một test FAIL có chủ ý lại là evidence tốt?

### Câu 3

Nếu Product B đứng #1 theo score 9.60, bạn được phép kết luận gì?

### Câu 4

Vì sao không đổi `RANK_SCENARIO` thành một câu tiếng Việt hoàn toàn trong code?

### Câu 5

Test PASS có phải market evidence không?

<details>
<summary><strong>Đáp án / Rubric</strong></summary>

**Câu 1**  
`go run` quan sát runtime behavior; `go test` so behavior với expectation đã mã hóa.

**Câu 2**  
Nó chứng minh test mới thực sự phát hiện behavior đang thiếu/sai. Nếu chưa từng thấy test fail trong tình huống nó phải fail, ta chưa có bằng chứng mạnh rằng test đang bảo vệ đúng thứ.

**Câu 3**  
Chỉ được kết luận Product B đứng #1 **theo input và formula hiện tại**. Không được kết luận B là sản phẩm Affiliate tốt nhất ngoài thị trường.

**Câu 4**  
`RANK_SCENARIO` là stable machine token có thể được dùng trong test, schema và code downstream. Ta giữ token và thêm diễn giải tiếng Việt cho learner.

**Câu 5**  
Không. Đây là software/test evidence. Market evidence cần observation từ nguồn thực tế.

**Blocking misconceptions:**

- test PASS = business truth;
- score #1 = product tốt nhất;
- test FAIL luôn là xấu;
- sửa nhiều thứ cùng lúc để “nhanh hơn”;
- machine token có thể đổi tùy ý.

</details>

---

## 15. Explain-back bắt buộc

Không nhìn đáp án, hãy giải thích bằng lời của bạn:

> “Tôi thêm một behavior mới cho Bot. Tôi sửa test trước nên test FAIL. Failure này cho tôi biết test thực sự phát hiện behavior đang thiếu. Sau khi sửa code, test PASS. PASS chứng minh implementation khớp expectation, nhưng không chứng minh ranking là sự thật kinh doanh. `RANK_SCENARIO` vẫn được giữ vì đó là contract kỹ thuật.”

Bạn không cần dùng đúng câu trên. Quan trọng là phải có đủ logic:

```text
change
→ expected behavior
→ intentional failure
→ fix
→ PASS
→ phạm vi kết luận
```

## 16. Tiêu chí PASS Bài 0.1

Bạn chỉ nên đánh dấu PASS khi có thể chứng minh:

- [ ] chạy được `go run ./cmd/bot`;
- [ ] chạy được `go test ./...`;
- [ ] biết hai lệnh trả lời hai câu hỏi khác nhau;
- [ ] đã ghi baseline trước khi sửa;
- [ ] đã tạo ít nhất một thay đổi behavior nhỏ;
- [ ] đã nhìn thấy một test FAIL có chủ ý;
- [ ] đã sửa tới PASS;
- [ ] biết test PASS chỉ chứng minh requirement đã mã hóa;
- [ ] không coi ranking baseline là market truth;
- [ ] hiểu vai trò của stable token như `RANK_SCENARIO`;
- [ ] lưu được before / failure / change / after;
- [ ] explain-back được toàn bộ vòng trên bằng lời của mình.

## 17. Bạn chưa cần học gì ở đây?

- database;
- HTTP API;

- AI/LLM;

## 18. Cầu nối sang Bài 0.2

Sau Bài 0.1, bạn đã biết:

```text
Bot có thể chạy đúng theo code.
```

Nhưng một câu hỏi lớn xuất hiện:

> **“Dữ liệu Bot đang đọc có phải dữ liệu thật không? Và từng con số trong đó thực sự là fact, estimate hay chỉ assumption?”**

Đó chính là Bài 0.2.

Ở bài tiếp theo, bạn sẽ học hai trục phân loại cực kỳ quan trọng:

```text
Evidence kind:
real / test / synthetic / replay

Claim kind:
fact / estimate / assumption / unknown
```

Nếu không nắm được hai trục này, một Bot có output rất đẹp vẫn có thể tạo ra **false confidence** — cảm giác chắc chắn giả tạo.
