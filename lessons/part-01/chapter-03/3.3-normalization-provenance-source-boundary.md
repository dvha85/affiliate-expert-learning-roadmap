# Bài 3.3 — Normalization, provenance và source boundary nhỏ nhất

> **Mục tiêu:** biến input đã validated thành canonical observation có thể so sánh về sau, nhưng vẫn giữ đủ provenance/raw meaning để reviewer biết value đến từ đâu và normalization đã làm gì.

Bài này là knowledge pull cuối của **M01 Checkpoint 1 / Chương 03**. Sau bài, output chưa phải history store; output là một canonical validated observation sẵn sàng cho Chương 04.

## 1. Trigger — Validation đúng nhưng data vẫn khó so sánh

Hai nguồn có thể biểu diễn cùng kiểu value khác nhau:

```text
Source A: "10%"
Source B: 0.10
```

hoặc:

```text
Source A: "299.000 ₫"
Source B: 299000 VND
```

Nếu Bot muốn compare/history, nó cần normalized form.

Nhưng nếu normalization chỉ giữ:

```text
commission_rate = 0.10
```

mà xóa mất source/raw representation, reviewer có thể không biết:

- value được source hiển thị thế nào;
- parser đã transform gì;
- unit/currency ban đầu là gì;
- claim là source-displayed hay derived.

Do đó:

```text
Normalize
≠ erase provenance
```

## 2. Try First — Normalize bằng tay trước

Chọn một observation M00 thật.

Ghi hai cột:

| Raw/source representation | Canonical value |
|---|---|
| `10%` | `0.10` |
| `299.000 ₫` | `299000`, `VND` |
| `2k+ sold` | giữ text signal, không biến thành exact 2000 valid orders |

Sau đó tự hỏi:

1. Transformation nào deterministic?
2. Transformation nào cần assumption?
3. Raw value nào phải giữ để audit?
4. Field nào không nên normalize thành một meaning mạnh hơn source?

## 3. Validation khác normalization

### Validation

Hỏi:

```text
Input này có hợp contract để ingest không?
```

### Normalization

Hỏi:

```text
Nếu hợp lệ, ta biểu diễn value nhất quán thế nào để downstream compare được?
```

Ví dụ:

```text
"10%"
→ parse/validate format
→ normalize 0.10
```

Nhưng:

```text
"Best seller"
```

không nên normalize thành:

```text
quality_score = 0.95
```

nếu không có method/evidence.

## 4. Raw, normalized và derived phải tách nghĩa

Mental model:

```text
Raw/source evidence
        ↓
Normalization
        ↓
Canonical observed value
        ↓
Derived calculation / decision
```

Ví dụ:

```text
Raw: "10%"
Normalized observed: commission_rate = 0.10
Derived: price × commission_rate = 50000
```

Ba tầng này không giống nhau.

Nếu downstream chỉ còn derived number, audit trail bị yếu.

## 5. Provenance tối thiểu phải sống qua normalization

Canonical observation M01 cần giữ ít nhất:

```text
subject_id
observation_id
source_url
observed_at
ingested_at
access_method
evidence_kind
```

và đủ context để hiểu normalized values.

Không nhất thiết mọi field đều cần `raw_*` machine field riêng ở M01. Nhưng nếu normalization làm thay đổi representation đáng kể, implementation/artifact phải cho reviewer truy được transformation.

Ví dụ có thể dùng:

```text
notes/raw capture
```

hoặc structured raw field nếu thật sự cần test/query.

Không over-engineer universal provenance schema ở Chương 03.

## 6. Source boundary là gì?

Source boundary trả lời:

> Code nào chịu trách nhiệm biến source-specific input thành canonical observation?

Ở M01, learner path đơn giản nhất có thể là:

```text
JSON/manual file
→ decoder
→ validate
→ normalize
→ canonical observation
```

Nếu sau này có source khác:

```text
Source A adapter ─┐
                  ├→ canonical observation
Source B adapter ─┘
```

Nhưng Chương 03 **không bắt buộc** bạn phải xây interface hierarchy trước khi có source thứ hai.

Nguyên tắc:

> **Boundary trước, abstraction chỉ khi có nhu cầu thật.**

## 7. Vì sao không nên xây generic adapter framework ngay?

Người mới có thể bị cuốn vào:

- interfaces;
- factories;
- dependency injection;
- plugin registry;
- retry/network code.

Nhưng M01 hiện chỉ cần public/manual local input.

Một function/package nhỏ có boundary rõ đã đủ:

```text
Load → Validate → Normalize
```

Khi Mission sau có automated source/tool, ta mới mở rộng.

## 8. Normalization rule phải deterministic và explainable

Rule tốt:

```text
10% → 0.10
```

vì transformation rõ.

Rule tốt:

```text
"VND" và "₫" → canonical currency VND
```

nếu source context đủ rõ.

Rule nguy hiểm:

```text
"2k+ sold" → sold_count = 2000
```

vì `2k+` không có nghĩa exactly 2000, và `sold` chưa chắc là Affiliate valid orders.

Rule nguy hiểm:

```text
seller badge "top" → demand_score = 0.9
```

nếu method chưa tồn tại.

## 9. Normalization không được nâng claim kind

Từ bài 0.2:

```text
source displays "best seller"
```

có thể là fact về source display.

Sau normalization, nó vẫn không tự thành:

```text
Product objectively best-selling market-wide
```

Normalization thay representation, không nâng mức chắc chắn của claim.

> **Clean data shape không tạo stronger evidence.**

## 10. Currency normalization không đồng nghĩa FX conversion

Nếu source ghi:

```text
₫299,000
```

normalize thành:

```text
price = 299000
currency = VND
```

là hợp lý.

Nhưng nếu một record USD và một record VND:

```text
normalization
```

không tự giải quyết mixed-currency comparison.

FX conversion cần rate source/time riêng và chưa phải scope Chương 03.

Mixed currency vẫn có thể cần `HUMAN_REVIEW` ở decision layer.

## 11. `observed_at` phải đi theo source evidence, không theo normalize time

Pipeline:

```text
observed_at = t1
normalize at t2
```

Không được đổi:

```text
observed_at = t2
```

chỉ vì canonical record được tạo ở t2.

Nếu cần, `ingested_at`/processing metadata mới phản ánh t2.

Đây là nền tảng để Chương 04 xử lý late/out-of-order observations đúng.

## 12. Apply — Tạo canonical ingest path

Refactor nhỏ theo flow:

```text
raw JSON/file
→ strict decode
→ validate
→ normalize
→ canonical observation
```

Yêu cầu:

- M00 fields tiếp tục được đọc;
- `subject_id` được giữ;
- provenance/time không mất;
- normalized rate/currency nhất quán;
- missing vẫn missing;
- no derived ranking fact được ghi ngược vào observed evidence;
- code path có test/executable usage thật.

## 13. Failure case — Normalization làm mất raw meaning

Raw:

```text
other_visible_signal = "2k+ sold"
```

Implementation sai:

```text
sold_count = 2000
other_visible_signal bị xóa
```

Vấn đề:

```text
approximate seller signal
→ exact numeric fact
```

Expected:

```text
preserve raw signal
+ nếu tạo derived interpretation thì label method/limitation rõ
```

## 14. Failure case — Normalization invents currency

Input:

```text
price = 299000
currency missing
```

Sai:

```text
currency = VND vì learner đang ở Việt Nam
```

Đúng:

```text
currency remains missing
→ decision eligibility xử lý sau
```

Không lấy user locale làm market evidence.

## 15. Failure case — Adapter làm mất source provenance

Nếu source-specific parser chỉ trả:

```text
Product{Price: 299000}
```

nhưng bỏ source/time/access metadata, downstream không audit được value.

Canonical output phải giữ provenance.

## 17. Chương 03 chứng minh gì — và chưa chứng minh gì?

Chứng minh:

- identity semantics rõ hơn;
- malformed/invalid input fail rõ;
- canonical values nhất quán;
- provenance survive normalization;
- missing không bị invent;
- ingest path đủ để tạo validated observations.

Chưa chứng minh:

- history immutable;
- persistence survive restart;
- delta đúng;
- freshness policy đúng;
- source automation;
- AI grounding.

Những phần đó thuộc Chương 04/M02.
