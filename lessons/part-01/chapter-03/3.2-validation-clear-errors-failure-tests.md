# Bài 3.2 — Validation contract, clear errors và failure-path tests

> **Mục tiêu:** sau bài này, ingest M01 phải phân biệt được record parse được với record hợp lệ, fail rõ khi input malformed/invalid, và không silently ignore field có thể làm thay đổi meaning của evidence.

Bài này vẫn thuộc **M01 Checkpoint 1**. Bạn chỉ mở sau khi đã có `subject_id`/observation identity rõ từ 3.1 và đã thử ít nhất một invalid case trên ingest hiện tại.

## 1. Trigger — Parse được chưa có nghĩa dùng được

Một JSON như sau có thể parse hoàn toàn bình thường:

```json
{
  "subject_id": "P-1",
  "observation_id": "OBS-1",
  "product_name": "Product X",
  "source_url": "https://example.com/x",
  "observed_at": "2026-08-31T10:00:00+07:00",
  "price": -100,
  "currency": "VND",
  "commission_rate": 1.5
}
```

Parser có thể đọc được syntax.

Nhưng business/domain validation phải nói:

```text
price < 0 → invalid
commission_rate > 1 → invalid
```

Vì vậy:

```text
parse success
≠ validated evidence
```

## 2. Try First — Test invalid records trước khi học rules

Tạo scratch cases:

```text
A. malformed JSON
B. unknown field: commission_percent_text
C. price = -1
D. commission_rate = 1.5
E. source_url missing
F. observed_at invalid
G. subject_id missing
```

Chạy ingest/test hiện tại.

Ghi:

```text
Case:
Expected:
Observed:
Was it silently accepted?
Error clear enough to fix input?
```

Mục tiêu là nhìn thấy **failure behavior hiện tại**, không đoán implementation tối ưu.

## 3. Ba tầng không được trộn

Mental model:

```text
Decode / Parse
→ Structural validation
→ Domain/evidence validation
```

### Decode / Parse

Hỏi:

> Input có đúng cú pháp JSON/type cơ bản để đọc không?

### Structural validation

Hỏi:

> Required fields/shape có đủ không?

Ví dụ:

```text
subject_id missing
observation_id missing
source_url missing
```

### Domain/evidence validation

Hỏi:

> Value có hợp nghĩa trong contract hiện tại không?

Ví dụ:

```text
price negative
commission_rate > 1
real evidence nhưng source_url không phải http(s)
```

Tách tầng giúp error message rõ hơn.

## 4. Strict input tốt hơn silent acceptance ở canonical ingest

Go JSON decoder mặc định có thể bỏ qua unknown field tùy cách dùng.

Ở canonical ingest M01, silent ignore có rủi ro:

```text
learner gõ nhầm commission_rate → commision_rate
→ decoder bỏ qua field lạ
→ commission_rate trở thành missing
→ downstream behavior khác mà không biết vì sao
```

Vì vậy policy tốt cho canonical ingest là:

```text
unknown field
→ clear rejection
```

hoặc nếu bạn thiết kế quarantine path:

```text
unknown field
→ explicit quarantine / not eligible
```

Không được:

```text
unknown field
→ silently ignored
→ declare validated
```

## 5. Validation không được invent value

Nếu:

```text
commission_rate = null
```

validation có thể nói:

```text
missing for ranking requirement
```

nhưng không được tự sửa thành:

```text
0
```

Tương tự, validation không được:

- tự đoán currency;
- tự đổi seller claim thành fact;
- tự dùng current time thay invalid observed_at;
- tự merge subject vì name giống.

> **Validation quyết định value có hợp contract không; validation không phải máy bịa value để làm record hợp lệ.**

## 6. Error message tốt phải giúp sửa đúng tầng

Error yếu:

```text
invalid input
```

Error tốt hơn:

```text
observation OBS-1: commission_rate phải nằm trong [0,1], got 1.5
```

Hoặc:

```text
record 2: unknown JSON field "commision_rate"; did you mean "commission_rate"?
```

Không cần xây hệ thống error framework phức tạp. Chỉ cần error:

- chỉ ra record/field;
- nói condition vi phạm;
- không che nguyên nhân;
- đủ deterministic để test.

## 7. Reject vs quarantine

M01 beginner path nên ưu tiên **reject rõ** cho canonical file import.

Quarantine chỉ đáng thêm nếu Mission thật sự cần giữ invalid raw record để review.

Nếu dùng quarantine, phải phân biệt:

```text
raw evidence preserved
≠ accepted canonical observation
```

Không để invalid record chảy vào history/scoring như record hợp lệ.

## 8. Required field phụ thuộc decision scope

Không phải mọi field imaginable đều required.

M01 canonical ingest chỉ cần các field phục vụ identity/provenance/baseline/history hiện tại.

Ví dụ:

```text
refund_rate
```

không nên trở thành required chỉ vì sẽ hữu ích sau này.

Nếu chưa quan sát:

```text
unknown
```

vẫn tốt hơn ép schema thành “đầy đủ”.

Nguyên tắc:

> **Schema vừa đủ + validation chặt cho field đang có giá trị hơn schema khổng lồ đầy giả định.**

## 9. Domain bounds phải có reason

Các rule như:

```text
price >= 0
commission_rate ∈ [0,1]
```

có semantics rõ.

Nhưng đừng invent:

```text
price phải < 10,000,000
```

nếu không có contract/source lý giải.

Validation rule phải trả lời được:

```text
Rule này bảo vệ failure nào?
Scope nào?
Có trường hợp hợp lệ nào bị reject không?
```

## 10. Failure taxonomy cho ingest

| Failure | Ví dụ | Expected family |
|---|---|---|
| Syntax | JSON thiếu `}` | parse error |
| Shape | thiếu `subject_id` | validation error |
| Domain | price âm | validation error |
| Provenance | real + sample URL | validation error |
| Identity | observation ID conflict | conflict/review |
| Unknown field | typo/new field | reject/quarantine theo policy |
| Missing business input | commission null | canonical observation có thể lưu, nhưng decision eligibility có thể `GET_MORE_DATA` |

Điểm cuối rất quan trọng:

```text
valid observation
≠ sufficient decision input
```

Một observation có thể trung thực nhưng thiếu commission. History vẫn có thể cần lưu việc “source không cung cấp commission”.

## 11. Không biến validation thành ranking gate duy nhất

M00 `DecisionIssues()` kiểm vài field để quyết định ranking đầu tiên có nên chạy.

M01 cần tách dần:

```text
Canonical ingest validity
```

khỏi:

```text
Decision eligibility
```

Ví dụ:

```text
subject_id/source/time valid
commission_rate missing trung thực
```

Record có thể **valid evidence** để lưu history, nhưng chưa đủ cho commission-per-order ranking.

Nếu ta reject mọi missing scoring field khỏi ingest, Bot sẽ mất evidence rằng field đó từng missing.

## 12. Apply — Viết validation contract nhỏ

Trên code hiện có:

1. bật/implement strict unknown-field handling;
2. thêm validation cho `subject_id`, `observation_id`, source/time và numeric bounds cần thiết;
3. giữ missing scoring field khác invalid value;
4. error có field/context rõ;
5. không làm regression M00 behavior.

Tạo table test hoặc nhiều case đơn giản nếu phù hợp trình độ hiện tại.

Không bắt buộc học table-driven test nếu chính pattern đó làm bạn mất focus; behavior quan trọng hơn style.

## 13. Test failure bắt buộc

Ít nhất chạy:

```text
malformed JSON
unknown field
negative price
missing subject_id
```

Và một case:

```text
commission_rate = null
```

để chứng minh bạn phân biệt:

```text
invalid record
```

với:

```text
valid-but-incomplete evidence
```

## 14. Case — Typo bị silent ignore

Input:

```json
{
  "commission_rtae": 0.1
}
```

Nếu decoder silently ignore và code tiếp tục, đây là failure của ingest contract.

Expected:

```text
reject unknown field
```

hoặc explicit quarantine.

## 15. Case — Missing không phải invalid zero

Input:

```text
commission_rate = null
missing_fields = [commission_rate]
```

Nếu source thật không cung cấp commission, observation vẫn có thể là E1 evidence hợp lệ về những field khác.

Expected:

```text
canonical evidence may be accepted
ranking may GET_MORE_DATA
```

Không:

```text
null → 0
```

## 16. Evidence cần lưu

- before behavior cho invalid cases;
- validation rule list + reason;
- unknown-field policy;
- malformed/unknown/negative/missing tests;
- một case valid-but-incomplete;
- before/after error output;
- final `go test ./...`.

## 17. Checkpoint

1. Parse success khác validation success thế nào?
2. Vì sao canonical ingest không nên silently ignore unknown field?
3. Missing commission có nhất thiết làm observation invalid không?
4. Validation có được tự điền default 0 không?
5. Observation valid có đồng nghĩa đủ để rank không?
6. Error message tốt cần chứa gì?

<details>
<summary><strong>Đáp án/rubric</strong></summary>

- Parse chỉ chứng minh syntax/type đọc được; validation kiểm contract/semantics.
- Vì typo/new material field có thể làm evidence bị hiểu sai mà không báo.
- Không; có thể là valid-but-incomplete evidence.
- Không, trừ khi 0 được source thực sự quan sát/contract quy định rõ.
- Không.
- Field/context + rule vi phạm, đủ để sửa/reproduce.

**Blocking misconceptions:**

- parse được = data đúng;
- missing = invalid = zero;
- reject càng nhiều field càng trustworthy;
- silent ignore giúp compatibility nên luôn tốt.

</details>
