# Bài 3.1 — Stable subject identity, observation identity và schema vừa đủ

> **Mục tiêu:** sau bài này, bạn phải phân biệt được Product/subject với từng observation, thêm stable `subject_id` vào record M00 mà không viết lại parser từ đầu, và giữ `observed_at` khác `ingested_at`.

Bài này thuộc **M01 Checkpoint 1**. Bạn chỉ mở bài sau khi đã thử đưa input xấu/ambiguous qua ingest hiện tại và thấy ít nhất một gap về identity hoặc schema.

## 1. Trigger — Gap vừa xuất hiện là gì?

M00 đã có `observation_id`, `product_name`, `source_url`, `observed_at` và các value cần cho baseline.

Nhưng M01 muốn trả lời:

```text
Product này thay đổi thế nào qua thời gian?
```

Để trả lời, Bot phải biết:

```text
observation t1
và
observation t2
```

có thuộc **cùng một subject** hay không.

Nếu chỉ dựa vào `product_name`, hai lỗi rất dễ xảy ra:

```text
Tên giống nhau nhưng là hai Product khác nhau
```

hoặc:

```text
Cùng Product nhưng tên hiển thị đổi theo campaign/thời điểm
```

Đây là lý do M01 cần stable identity.

## 2. Try First — Thử trước trong 10 phút

Lấy hai record scratch.

Case A:

```text
observation_id: OBS-001
product_name: Super Blender
observed_at: t1
```

Case B:

```text
observation_id: OBS-002
product_name: Super Blender - Sale 8.8
observed_at: t2
```

Tự trả lời trước khi đọc tiếp:

1. Đây có chắc là cùng Product không?
2. `observation_id` có thể dùng để nói chúng cùng Product không?
3. `product_name` có đủ ổn định để làm identity không?
4. Field nào còn thiếu để Bot compare history an toàn?

Lưu câu trả lời ban đầu vào artifact M01.

## 3. Mental model — Subject khác Observation

Dùng mô hình:

```text
Subject / Product
        │
        ├── Observation 1 @ t1
        ├── Observation 2 @ t2
        └── Observation 3 @ t3
```

### `subject_id`

Đại diện cho đối tượng ổn định cần theo dõi qua thời gian.

Ví dụ:

```text
subject_id: PRODUCT-ABC
```

### `observation_id`

Đại diện cho **một lần quan sát cụ thể**.

Ví dụ:

```text
OBS-ABC-20260831-1000
OBS-ABC-20260903-1000
```

Hai observations có thể:

```text
subject_id giống nhau
observation_id khác nhau
```

Đây chính là shape M01 cần.

## 4. Vì sao không dùng `product_name` làm stable identity?

Tên là display data, không phải identity contract mạnh.

Tên có thể thay đổi vì:

- campaign prefix/suffix;
- typo;
- localization;
- seller rename;
- package variant;
- formatting;
- promotion label.

Nếu Bot group history bằng tên, một rename có thể làm history bị tách thành hai Product.

Ngược lại, hai seller có thể cùng dùng tên giống nhau và Bot vô tình merge history.

Nguyên tắc:

> **Display label giúp con người đọc; stable identity giúp hệ thống nối evidence qua thời gian.**

## 5. `subject_id` nên đến từ đâu?

Ở M01 không cần universal global identity system.

Ưu tiên theo độ mạnh khi có thể:

```text
platform/domain stable product identifier
→ stable canonical URL/key đã kiểm
→ learner-assigned local subject_id có mapping note
```

Nếu source không có stable public ID, local `subject_id` vẫn hợp lệ nếu bạn ghi rõ mapping basis.

Ví dụ:

```text
subject_id: LOCAL-SUBJECT-001
identity_basis: canonical product page observed manually
```

Không được giả rằng một ID tự nghĩ ra chứng minh global identity ngoài thị trường.

## 6. `observed_at` khác `ingested_at`

Đây là distinction quan trọng thứ hai.

```text
observed_at
= khi source/thế giới được quan sát
```

```text
ingested_at
= khi Bot nhận/lưu observation
```

Ví dụ:

```text
observed_at = 10:00
ingested_at = 10:20
```

Không có vấn đề gì.

Nếu bạn import một file cũ ngày hôm sau:

```text
observed_at = hôm qua 10:00
ingested_at = hôm nay 09:00
```

vẫn hợp lệ nếu provenance trung thực.

Sai nguy hiểm:

```text
import file hôm nay
→ ghi observed_at = now
```

Nếu data thực ra được quan sát hôm qua, bạn vừa làm evidence trông mới hơn thực tế.

## 7. Schema M01 tối thiểu

Evolve record M00 thành semantic shape:

```yaml
subject_id:
observation_id:
product_name:
source_url:
observed_at:
ingested_at:
access_method: public_manual
evidence_kind: real
price:
currency:
commission_rate:
other_visible_signal:
missing_fields: []
notes:
```

Bạn chưa cần:

- database primary key phức tạp;
- seller master table;
- universal catalog;
- event sourcing framework;
- ORM;
- UUID nếu local deterministic ID đã đủ.

Schema chỉ nên đủ để phục vụ Mission.

## 8. Evolve code hiện có, không viết lại từ đầu

M00 đã có `observation.Record` và JSON loader.

Cách học đúng:

```text
existing Record
→ thấy identity/time gap
→ thêm field nhỏ nhất
→ update fixture/test
→ chạy lại
```

Không nên:

```text
xóa package cũ
→ thiết kế lại toàn bộ domain model
→ thêm repository/service/factory
```

Nếu implementation cũ đang chạy và có tests, hãy tận dụng nó làm before evidence.

## 9. Identity assumptions phải nhìn thấy được

Ví dụ bạn map hai URLs vào cùng `subject_id` vì tin đó là cùng Product.

Nếu basis yếu, ghi:

```text
identity_confidence: low
identity_note: same seller page redirects to same canonical product URL
```

Ở M01 không nhất thiết thêm các field này vào machine schema nếu không cần. Nhưng reasoning artifact phải nói được **vì sao bạn coi hai observations là cùng subject**.

## 10. Failure case — Same name, different subject

Input:

```text
A: product_name = "USB Hub 7-in-1"
B: product_name = "USB Hub 7-in-1"
```

nhưng source URLs/sellers khác.

Bot không được tự merge chỉ vì tên giống.

Expected handling:

```text
identity unresolved
→ distinct subject_id hoặc HUMAN_REVIEW ở layer phù hợp
```

## 11. Failure case — Same subject, renamed display label

```text
OBS-1
subject_id = PRODUCT-X
product_name = "Desk Lamp"

OBS-2
subject_id = PRODUCT-X
product_name = "Desk Lamp - Summer Sale"
```

Tên đổi không tự tạo Product mới.

History grouping phải dựa vào `subject_id`.

## 12. Failure case — Observation ID bị reuse

Nếu:

```text
OBS-001 @ t1
OBS-001 @ t2
```

với content khác nhau, đây không phải “update observation cũ” mặc định.

Ở M01, observation phải có identity riêng. Reuse ID với content khác là conflict cần xử lý rõ ở bài 3.2/Chương 4.

## 13. Apply — Sửa record M00 hiện tại

Thực hiện trên branch learner của bạn:

1. thêm `subject_id`;
2. thêm/ghi rõ `ingested_at` theo implementation bạn chọn;
3. cập nhật JSON fixture cần thiết;
4. giữ `observation_id` riêng;
5. không đổi missing thành zero;
6. chạy tests hiện có;
7. thêm test chứng minh same subject có thể có different observation IDs.

Lưu:

```text
Before record shape:
Change:
After record shape:
Why subject_id is needed:
Why observed_at != ingested_at:
```

## 14. Test một failure

Tạo test/case:

```text
same product_name
+ different subject_id
```

và chứng minh code không tự group/overwrite dựa chỉ trên name.

Hoặc nếu code chưa có grouping, test validation/fixture semantics và ghi rõ grouping thuộc Chương 04.

Điều tuyệt đối không được xảy ra:

```text
product_name equality
→ silently treated as identity truth
```

## 15. Evidence cần lưu

- attempt trước bài;
- ambiguous identity case;
- before/after record shape;
- test cho `subject_id` vs `observation_id`;
- ví dụ `observed_at` vs `ingested_at`;
- note identity basis cho ít nhất một real Product từ M00;
- final test output.

## 16. Checkpoint

1. `subject_id` và `observation_id` khác nhau thế nào?
2. Vì sao `product_name` không đủ làm stable identity?
3. Khi import file cũ hôm nay, `observed_at` nên là hôm nay hay thời điểm thật sự quan sát?
4. `ingested_at` dùng để trả lời câu hỏi gì?
5. Same name có chứng minh same subject không?
6. Same subject có thể có nhiều observation IDs không?

<details>
<summary><strong>Đáp án/rubric</strong></summary>

- `subject_id` nối cùng đối tượng qua thời gian; `observation_id` định danh một lần quan sát.
- Name là display data có thể đổi/trùng.
- Giữ thời điểm thật sự quan sát.
- Khi Bot nhận/lưu record.
- Không.
- Có, đó là expected history shape.

**Blocking misconceptions:**

- observation ID = product ID;
- name giống = cùng Product;
- import time = observation time;
- thêm nhiều field hơn luôn làm schema đáng tin hơn.

</details>
